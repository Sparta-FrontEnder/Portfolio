# 公司程序员以为她的 Title 写错了

“你是不是应该去找 HR？你的 Title 好像写错了。”

公司的一位程序员看完她做的系统后，很认真地提醒她。他以为她是新来的软件工程师，只是员工资料里的职位没有更新。

但她的 Title 没有写错。她是一名 Data Scientist。几个月前，她会写 SQL 和基础 Python，熟悉公司的业务数据，却从未独立开发过一个完整应用。

当公司里其他人还在用 AI vibe coding，做出来的东西大多只有一个 Dashboard 和一套 fake data 时，她已经完成了一套真正可以使用的 React + C#/.NET 应用：接入真实业务数据、提供 Service 和 API、持续刷新数据，并把原本约10分钟的数据等待压缩到1秒以内。

后来，这套系统成了公司的样板产品。其他团队开始参考它的结构，把它作为开发内部应用的模板。

这个故事真正值得讨论的不是“一个不会写代码的人突然学会了写代码”，而是当 AI 让代码越来越便宜，一个真正懂业务的人，在资深程序员的指导下，能够产生多大的价值。

## 她不懂完整开发，但她懂最重要的东西

我当时受邀为一家通信设备测试、维修和物流服务公司提供技术咨询，与我合作的就是这位 Data Scientist。

她没有完整的前后端开发经验，不清楚 React 如何调用后端，不知道为什么要拆 Service 和 API，也没有独立维护过由前端、后端和数据库组成的应用。

但她知道公司的数据代表什么。

她知道一个设备从接收、测试、维修到出库会经历哪些状态；知道哪些指标可以合并，哪些口径绝对不能混；也知道管理层看到什么信息后才能做出决策。

这些知识很难从代码仓库里读出来，也不是把数据库 schema 发给 AI 就能自动获得的。程序员可以在几天内写出一个漂亮的 Dashboard，却可能花几个月才能理解页面上的数字为什么是对的。她恰好相反：她不会搭完整应用，但从一开始就知道什么结果才有业务意义。

过去，这种能力必须等待程序员来“翻译”。她提出需求，程序员理解，再将其变成软件。每经过一层沟通，信息都会损失一些。

AI 改变了这条价值链。它让她第一次有机会把业务判断直接变成可以运行的东西。

## Dashboard + fake data，不等于产品

当时，公司内部也有人开始尝试 vibe coding。

用提示词生成一个页面并不难。放几张图表、几组卡片，再准备一份 fake data，一个看起来像产品的 Dashboard 很快就能出现。

但 Demo 和产品之间仍然隔着很长一段距离。

一个真正的内部应用必须回答：

- 数据从哪里来，多久更新一次？
- 前端怎样调用后端？
- API 失败时页面显示什么？
- 不同业务状态怎样映射？
- 查询太慢时如何优化？
- 谁负责日志、排错和维护？
- 原作者离开后，其他人敢不敢继续修改？

Fake data 永远不会延迟，不会缺字段，也不会违反业务规则。真实数据会。

Vibe coding 可以让一个人快速到达“能演示”，但从“能演示”走到“能被公司依赖”，仍然需要完整的工程过程。

她最终做出来的不是一个套着数据的页面，而是一套完整应用。前端、Service、API、数据缓存和 AI 分析共同工作，页面展示的是持续刷新的真实业务数据，而不是为 Demo 准备的数字。

这也是为什么公司程序员误以为她的职位写错了。他看到的不是一个 Data Scientist 做的实验，而是一个软件工程师应该交付的产品。

## AI 没有负责把她变成程序员

如果只是给她一个 Cursor 账号，再告诉她“用 AI 把系统做出来”，结果很可能和其他 vibe-coded Dashboard 没有区别。

AI 能生成代码，但它不会自动教会一个人当前任务位于系统的什么位置，为什么前后端要分开，哪些地方需要日志和错误处理，也不会自动证明一个看起来正确的数字真的符合业务口径。

我的角色不是替她把所有代码写完，也不是站在旁边看她不断重新生成。我做的第一件事，是先给她一张地图：

```text
业务需求 → 前端页面 → API → Service → 数据库与缓存
```

在开始任何功能之前，她需要知道自己正在修改哪一层，上游输入是什么，下游又会受到什么影响。有了这张地图，AI 生成的代码才不再是一块从天而降、没人敢碰的黑盒。

然后，我们把真实需求拆成可以验收的小任务：先定义页面行为，再确认接口契约，接着明确读取哪些数据，最后处理空数据、错误和超时。

AI 可以生成第一稿，但她必须读懂并解释：

- 这段代码在做什么？
- 为什么放在这一层？
- 如果数据为空会发生什么？
- API 失败时用户会看到什么？
- 怎样证明结果符合业务口径？

讲不清楚的代码不能合并。遇到错误时，先看日志、返回值和真实数据，再去问 AI，而不是不断点击“再试一次”。

随着项目推进，我逐渐把独立模块交给她。最开始她修改页面，后来开始增加 Service 和 API，最后能够自己排查问题并解释系统的基本架构。

AI 提高了她的速度，但真正让她成长的，是一套不能跳过理解、验证和复盘的流程。

## 10分钟到1秒，靠的不是再写一遍代码

这个项目中最能体现资深工程师价值的，是一个性能问题。

Dashboard 背后的数据库查询和数据刷新大约需要10分钟。如果用户每次打开页面都等待完整查询，系统即使功能全部正确，也没有实际使用价值。

最直觉的方案是加 Redis，AI 也很容易给出这个答案。但公司政策不允许使用 Redis。

这时，如果只是继续 vibe coding，常见做法是让 AI 换一种写法、增加线程或反复调整查询。资深工程师的优势不在于能把同一段代码手写得更快，而在于会先重新定义问题：为什么昂贵查询发生在用户请求路径上？哪些数据必须实时，哪些允许延迟刷新？在不能使用 Redis 的约束下，什么方案最容易维护？

我们最终没有继续压榨那条10分钟的路径，而是改变了数据流。

系统定时把常用数据推入应用侧的 SQLite 缓存。昂贵的数据准备发生在用户请求之外，Dashboard 和 AI 分析读取已经准备好的热数据。最终，页面原本约10分钟的数据等待被压缩到1秒以内。

SQLite 不够时髦，但它符合公司政策，也适合当时的数据量、刷新频率和团队维护能力。正确的架构不是技术名词最多的架构，而是在真实限制下解决问题的架构。

真正的优化，很多时候不是让原来的路径再快一点，而是意识到这件事根本不应该发生在用户点击的那一刻。

## 为什么懂业务的人变得更值钱

AI 降低的是“从零写出第一版代码”的门槛，没有降低“对不对、能不能上、坏了怎么查”的门槛。

当第一版代码越来越容易获得，价值自然会向代码之前移动。懂业务的人知道哪个问题值得解决、哪个指标才关键、哪些数据口径不能混用、一个功能什么时候才算完成，以及用户到底会不会使用它。

一个只会写代码但不懂业务的人，可能高质量地完成一个没有价值的需求。一个懂业务的人借助 AI，则可以更短地走完从问题到实现的距离。

她之所以能做出公司的样板产品，不是因为她突然掌握了所有编程知识，而是因为她原本就掌握最难被复制的部分：业务上下文和正确性判断。

AI 让这些判断第一次可以更直接地变成软件。

## 为什么资深程序员依旧不可替代

如果业务知识如此重要，是否意味着程序员不再重要？不是。

AI 让基础代码生产变便宜后，初级编码能力的稀缺性确实在下降。但资深工程师的价值本来就不只是写代码。

资深工程师能够把“Dashboard 太慢”重新定义成“用户请求路径中反复执行约10分钟的数据准备，同时受到不能使用 Redis 的政策约束”。他会把安全政策、预算、团队能力和维护成本从第一天放进架构，也会为 API 失败、数据过期、缓存异常和后续交接做设计。

更重要的是，他知道什么时候应该停止 AI。当数字对不上、两个方案互相冲突、连续生成没有改善时，正确动作不是再生成一次，而是回到数据和假设本身。

AI 可以快速回答“怎么写”，但这些判断决定的是“为什么这样写，以及这个答案是否值得上线”。

## 从一个人的项目，变成公司的模板

项目后期，她已经能够独立修改前端、增加 Service 和 API，并根据错误日志排查问题。

更重要的是，这套应用没有随着咨询结束变成无人维护的黑盒。它继续被公司使用，并成为其他团队开发类似内部工具时参考的样板。

成功不是让对方复制我的代码，也不是让她背完一套框架。成功是当我退出后，她仍然能够理解系统、判断结果、继续开发，并把这套方法带给其他人。

那位程序员以为她的 Title 写错了，其实正好说明了最终结果。

她没有换 Title。她扩展了自己原本的能力边界。

## 最好的组合，不是谁取代谁

这个故事不是在证明业务人员应该取代工程师。它证明的是，当 AI 进入软件开发后，价值正在向代码的两端移动。

在代码之前，业务人员决定做什么、为什么做、数据是否正确、结果是否真正有用。

在代码之后，资深工程师保证架构是否合理、性能是否满足真实使用、系统能否处理失败、代码是否可以维护和交接。

AI 负责快速生产中间的大量实现。

最好的组合不是业务人员独自 vibe coding，也不是资深程序员包办所有工作，而是：

> 懂业务的人决定做什么、结果对不对；资深程序员负责地图、架构和工程闸门；AI 快速写出第一版。

## 结语

AI 没有在一夜之间把她变成资深程序员。

AI 让她的业务判断可以直接变成代码，而资深程序员的指导，让这些代码最终成为了一个真正可运行、可维护、可复制的产品。

当公司其他人的 vibe coding 还停留在 Dashboard 和 fake data 时，她已经完成了一套接入真实数据的完整应用，并让它成为其他团队使用的模板。

未来，单纯“会写出代码”会越来越难以构成竞争力。

真正稀缺的，是理解业务的人，以及能够把业务可靠地变成系统的人。

最好的人，会同时具备这两种能力。
