# 当写代码不再是瓶颈：我如何设计一套可验证的 AI Agent 交付引擎

过去一年，我一直在尝试用 AI 提升设计稿到工程代码的交付效率。最初的问题很直接：怎样让模型更准确地还原 Figma？但随着模型、Cursor 和 Figma MCP 逐渐成熟，我发现真正限制交付的已经不是生成代码，而是如何稳定地验证代码。

一个模型可以很快写出页面，却不代表它能持续交付正确、可维护、符合设计的页面。它可能漏掉响应式状态，误解动态数据，或者在修复一个问题时破坏另一个区域。更麻烦的是，同一个 Agent 既负责实现又负责验收时，很容易延续上一轮的假设，看不见自己的错误。

因此，我构建了 `agent-harness`：一套面向 WordPress / Elementor 项目的本地 AI 交付引擎。它不试图制造一个无所不能的 Agent，而是把软件交付拆成可追踪、可停止、可复核的状态流。

## 问题不在生成，而在调度与验证

早期的工作流通常是：

1. 从 Figma 读取设计；
2. 在一个 Cursor 窗口里实现 Widget；
3. 在另一个窗口里进行验收；
4. 人工复制问题、修改记录和下一轮指令。

这种方式能运行，但存在四个结构性问题。

第一，调度依赖人。不同会话之间没有可靠的状态传递，人既要做工程判断，又要充当消息队列。

第二，验收不稳定。让同一个 Agent 反复检查自己的工作，会产生上下文锚定；只做截图像素对比，又无法解释差异是布局错误、内容变化，还是浏览器渲染造成的噪声。

第三，知识无法积累。一个项目中发现的响应式规则、Elementor 限制或常见错误，在下一个项目里还会重新发生。

第四，系统不知道什么时候应该停。如果 builder 和 verifier 对问题产生分歧，继续自动运行只会把错误建立在尚未确认的基础上。

`agent-harness` 的设计目标，就是把这些隐含流程变成显式协议。

## 一份状态，而不是多份真相

整个系统以 `state.json` 作为唯一权威状态。页面、section、当前轮次、验证结果、争议和人工批准都记录在其中。`plan.md`、dashboard 和日志只是这份状态的不同视图，不能各自维护另一套结论。

这一点看起来简单，却是多 Agent 系统能否稳定运行的基础。如果 builder 认为 section 已完成、verifier 认为仍需修改，而 dashboard 又显示正在等待人工确认，那么自动化程度越高，系统反而越混乱。

统一状态之后，每个 section 都会沿着明确的生命周期前进：

```text
pending → building → gating → verifying → fixing → passed
                                      ↘ disputed → halted
```

编排器负责推进状态，而不是让 Agent 自己决定下一步。Agent 可以提出结果，但没有权力绕过门禁。

## Build、Gate、Verify 与 Fix

一次标准循环由四部分组成。

### Build：让 Agent 专注于实现

Builder 读取设计上下文、项目规范和当前 section 的任务，生成或修改代码。多个 section 可以批量构建，以减少启动会话和重复读取上下文的成本。

但批量构建不意味着批量通过。每个 section 的验证、失败和争议仍然独立记录，避免一个区域的结果掩盖另一个区域的问题。

### Gate：能由脚本判断的，不交给模型

在调用 verifier 之前，系统先运行确定性检查，例如：

- 文件和产物是否存在；
- PHP、JSON 或配置结构是否合法；
- 必要字段和约束是否满足；
- 已晋升的项目规则是否被违反；
- 响应文件是否符合 schema。

LLM 擅长判断视觉层级、设计意图和实现合理性，但不应该浪费在“文件是否存在”或“JSON 能否解析”这类问题上。确定性检查更便宜、更快，也更可复现。

### Verify：每一轮都从空上下文开始

Verifier 使用独立进程、全新会话和只读工具。它不会继承 builder 的推理，也不会沿用上一轮 verifier 的结论。

这样做是为了降低锚定效应。如果上一轮错误地认为某个间距已经正确，保留上下文的 verifier 很可能继续为这个判断寻找理由。全新会话迫使它重新基于设计、实现和检查清单得出结论。

Verifier 输出结构化 findings，而不是一段模糊评价。每个问题都需要说明位置、严重程度、证据和建议动作，以便 builder 在下一轮准确处理。

### Fix：修复必须回应问题

Builder 收到 findings 后执行修改，并输出结构化 response，说明每一项问题如何处理。如果它不同意某个 finding，不能静默忽略，而必须明确提出 dispute。

系统还会设置轮次上限和“无进展”熔断。如果连续多轮没有减少问题，就停止循环，避免 Agent 在相同错误上无限消耗 token。

## 争议必须让整个系统停下来

我刻意没有采用“这个 section 有争议，先让其他 section 继续跑”的策略。

当 builder 和 verifier 对设计事实、技术约束或实现方式产生冲突时，系统进入 `halted` 状态，等待人通过 `resolve-dispute` 做出裁决。原因很简单：争议可能暴露的是一条全局假设错误。若其他任务继续建立在这条假设之上，返工成本会快速扩大。

自动化系统最重要的能力，不只是能持续运行，还要知道什么时候不该运行。

## Section 通过，不等于页面完成

所有 section 通过验证后，页面仍然不能自动进入下一阶段。系统会进入 `AWAITING_APPROVAL`，由人进行 final review。

这是因为局部正确并不等于整体正确。页面级问题通常包括：

- section 之间的节奏和视觉层级；
- 动效是否自然；
- 内容组合是否符合真实使用场景；
- 模板、动态数据和多种样本之间是否一致；
- 单独看都正确的组件，组合后是否产生冲突。

因此，人不再负责机械地搬运日志或重复检查每个 CSS 属性，而是负责页面级审美、业务判断和最终拍板。

## 让错误变成下一次的规则

如果系统只加速当前项目，它的价值仍然有限。真正重要的是让经验回流。

`agent-harness` 为规则设计了生命周期：

```text
observed → candidate → enforced → retired
```

当人工 review 发现漏检，或者同类问题在多个项目中重复出现，系统会记录问题、原因和出现频率。满足条件后，可以通过 `promote` 将其晋升为确定性检查、验证规则或工程知识条目。

例如，一个经常出现的 Elementor 容器宽度错误，最初可能只是 verifier 的文字提醒；重复发生后，它可以被转化为脚本检查。于是下一次项目不再需要模型重新“理解”这条经验。

这形成了一个闭环：

```text
人工发现问题
    ↓
记录遗漏与原因
    ↓
规则评分与晋升
    ↓
确定性检查或显式知识
    ↓
后续项目自动避免
```

相比让 Agent 拥有模糊的“长期记忆”，我更相信可审查、可版本控制、可撤销的显式规则。

## 为什么暂时不使用通用 Agent 框架

LangGraph 等框架能够提供图结构、持久化和编排能力，但当前系统最重要的不是支持更多节点，而是把权限和停止条件卡死：

- verifier 必须只读；
- dispute 必须阻塞全局；
- section 通过后仍需页面批准；
- gate 结果必须与模型判断合并；
- 客户项目不能复制出第二套规则真相。

因此，现阶段我选择手写一个范围明确的编排器。系统也刻意只支持 WordPress / Elementor，不同时宣称兼容 Shopify、React 和所有前端栈。范围越明确，状态和验证语义才越可靠。

## 当前边界

这套引擎已经完成状态管理、确定性 gate、Agent 循环、争议处理、页面门禁、dashboard 和规则晋升，但仍有几个薄弱环节。

首先，截图采集还没有在所有环境中稳定自动化。Dashboard 可以展示 Figma 与实现截图，但没有产物时，视觉验证仍不完整。

其次，`dry-run` 通过只意味着确定性检查干净，并不等于真正完成视觉验收。绿色状态必须说明它验证了什么，不能制造虚假的安全感。

最后，系统是否有效，最终要通过真实客户项目、不同页面类型和长期规则回流来证明，而不是由架构图证明。

## 结语

`agent-harness` 的核心并不是“让 AI 自动写完整个网站”，而是重新分配软件交付中的责任：

- 编排器管理顺序、状态与停止；
- 脚本负责客观事实；
- LLM 负责需要语义和视觉判断的部分；
- 人负责争议、页面级审查与最终批准；
- 规则系统把经验带到下一个项目。

当生成代码越来越便宜，工程价值会更多地转向约束、验证、状态管理和知识积累。一个可靠的 AI 工程系统，不是让模型拥有最大的自由，而是让每一种判断都发生在最适合它的位置，并且让系统在不确定时真正停下来。
