# 从手写页面到编排 AI：我的工作流进化，以及我对程序员价值的重新理解

2025 年下半年，我开始和设计师一起经营一家设计工作室。我的工作看起来和很多全栈工程师类似：分析客户需求，从工程角度提出解决方案，再把设计稿变成真正可以运行的产品。

设计师交付的通常只是页面，但客户需要的是完整业务。一个产品详情页背后，还要有商品上架、购买流程和数据管理；一个内部系统不仅要看起来正确，还要处理权限、并发和真实操作。我的职责，就是填补设计与可用产品之间的所有空白。

在这个过程中，我最先想解决的，是最直观也最重复的问题：如何更快地把 Figma 设计一比一还原成代码。

## 第一阶段：AI 只是我的辅助工具

2025 年中旬，AI 的工程能力远没有现在成熟。最开始，我仍然需要手写大部分前端代码，GPT 和 Gemini 更多是查询工具：解释框架 API、补全局部实现、帮助排查错误。

这种方式比完全不用 AI 快一些，但没有改变工作的本质。我仍然反复编写 React 跳转、组件结构和常见交互。设计稿里的每一个 section 都要手动拆分、实现、调整，再重新检查响应式效果。

对于预算有限的客户，这种交付方式很难持续。客户不会因为工程师写了更多代码就愿意支付更多费用，他们在意的是结果和交付速度。

于是，我开始逐渐减少手写代码。我把设计稿按 section 截图，把布局、字体、间距和交互细节交给 AI，让它先生成对应代码，再由我转换到不同平台、拆分工程结构并处理业务逻辑。

这是第一次明显的效率提升。但人的工作并没有消失，只是从“逐行编写”变成了“准备上下文、修复输出和重新组织代码”。

## 第二阶段：Cursor 改变了交付方式

后来，我开始高频使用 Cursor。文件拆分、文档编写、跨文件修改和代码补全可以直接发生在工程环境里，不再需要在聊天窗口和编辑器之间反复复制。

我的交付速度进一步提升，但新的瓶颈也逐渐暴露出来。

截图仍然很慢。响应式布局、动效和交互效果仍需要大量调试。更重要的是，AI 的输出会受到上下文窗口影响：同一个项目，在不同会话中可能得到不一致的实现；随着对话变长，模型还会忘记早期约束，或者用新的局部判断推翻之前的架构。

对于定制化项目，这个问题尤其明显。每位客户都有自己的设计语言，不能简单复制上一套页面。代码可能无法复用，但那些关于宽度、断点、组件边界和视觉还原的经验，应该能够复用。

## 第三阶段：Figma MCP 减少了上下文搬运

随着 MCP 被广泛使用，Figma 也提供了自己的 MCP 工具。AI 可以主动读取节点结构、尺寸、颜色和页面信息，不再完全依赖我手工截图和描述。

这使设计信息收集的人工工作量降低了约 80%。过去需要我逐个 section 截图、标注并解释的内容，现在可以由 Agent 自主获取。

但 MCP 解决的是“如何获得信息”，没有解决“如何稳定使用信息”。模型依然可能产生幻觉，不同上下文窗口的结果依然可能漂移。工具能力增强，并不自动带来可靠的工程流程。

因此，我开始把 20 多个客户项目中积累的经验整理成标准和 skill：响应式应该如何检查、容器宽度怎样设置、组件应该拆到什么程度、什么样的实现才算健康。

这些规则的价值不在于强迫每个项目长得一样，而是让不同设计、不同会话和不同 Agent 产出的代码，都满足一套可维护的工程底线。

到这个阶段，我在一个月内可以同时对接 6–8 位工作量不同的客户。最开始时，这个数字只有 1–2 位。

## 真正的分水岭：写出来已经不是最难的事

效率提高之后，我发现了一个有些反直觉的变化：制作不再是整个流程中最耗时的部分，验证才是。

AI 可以很快生成页面，但我仍然需要反复检查：

- 是否真正还原了设计，而不只是“看起来差不多”；
- 不同屏幕宽度下是否正常；
- 修改一个 section 后是否破坏了其他区域；
- 动态内容和真实数据是否会打破布局；
- 代码是否符合平台限制和项目规范。

生成速度越快，验证压力反而越大。因为系统能够在更短时间内制造更多“接近完成”的产物，而每一个都可能隐藏细小但重要的问题。

有一天，我读到关于 LLM reasoning 和多 Agent 协作的研究。其中一种思路给了我很大启发：让 Agent A 负责完成任务，Agent B 独立检查，再由 Agent A 根据检查结果修正。

这并不是一个复杂的新概念，但它准确击中了我的瓶颈。

## 第四阶段：从双 Agent 到可编排的循环

我构建了第一版双 Agent 工作流。

Working Agent 负责按照 plan 实现页面，并维护每个 section 的状态。当一个 section 进入待验证状态后，我把它交给独立的 Verify Agent。Verify Agent 输出一份 Markdown 验收日志；Working Agent 根据日志修改；当 Verify Agent 再也找不到问题时，它会更新 section 状态。

页面全部完成后，仍由人进行最终验收。

这套工作流让重复测试工作减少了接近 80%，但它仍然有一个明显问题：两个会话不能自动交流。我还是要把日志、状态和指令从一个窗口搬到另一个窗口。

换句话说，AI 已经承担了实现和检查，我却还在充当两个 Agent 之间的 API。

于是，下一步自然变成了 orchestration。

我加入了一套本地编排系统，用统一状态监控页面拆分、当前进度、Verify Agent 的 findings，以及 Working Agent 对每条问题的回应。Dashboard 让人可以观察整个过程，而不需要进入每个会话追踪细节。

当两个 Agent 对一个问题产生争议时，系统会停止，而不是继续在不确定的基础上运行。页面完成后，也必须经过人工 final review 才能进入下一页。重复出现的问题则可以被整理成规则，回流到后续项目。

目前这套 harness 聚焦 WordPress / Elementor。过去在 Shopify 和 React 项目中形成的经验参与了它的设计，但我没有让系统为了“支持所有平台”而牺牲边界和稳定性。

最终，设计到工程实现不再是一连串需要人手动推动的聊天，而变成了一条有状态、有门禁、有熔断机制的交付流程。

人的操作被压缩到几个关键动作：

1. 提供项目配置和设计上下文；
2. 观察系统状态并处理争议；
3. 在页面级别做最终审核。

## 如果 AI 不需要我亲自写代码，我的价值是什么？

完成这套系统之后，我开始认真思考一个问题：当我可以用自然语言描述系统，并让 AI 完成大部分代码时，我作为程序员的定位到底是什么？

我曾经把工程能力和写代码的速度联系得很紧。但现在，我越来越认为，代码只是工程决策的一种表达形式。

我和一个不懂工程的人之间的差距，主要不在于谁更会向 AI 提问，而在于以下几件事。

### 1. 知道如何拆分复杂问题

AI 能执行任务，但任务边界仍然决定结果质量。工程师需要知道一个页面应该怎样拆成 section，一个系统应该怎样拆成状态、权限和责任，以及拆分到什么程度才不会让协调成本超过收益。

### 2. 能把新工具放进已有的技术地图

看到多 Agent 验证的论文时，我能够把它和自己在交付中的瓶颈联系起来；看到 MCP 时，我关心的不是“它很新”，而是它能否消除设计上下文的人工搬运。

经验的价值，是帮助我们判断一项技术应该放在哪里，而不只是知道它存在。

### 3. 能为 Agent 建立工程约束

更长、更技术化的 prompt 并不一定更好。真正有效的是让 Agent 明确输入、输出、权限、停止条件和验收标准。

当这些约束被写成状态机、schema、只读权限和确定性检查时，prompt 才从一次性的指令变成了工程系统的一部分。

### 4. 足够“懒”，愿意持续消灭重复工作

这里的懒不是逃避工作，而是无法忍受同一件机械工作发生第三次。

第一次手动解决问题，第二次总结方法，第三次就应该思考能否让系统自动处理。很多自动化不是来自宏大的技术规划，而是来自工程师对重复劳动的耐心耗尽。

## 我现在如何理解 AI 时代的工程师

AI 没有让工程能力失去价值，反而让经验产生了更强的杠杆。

以前，一项架构判断最终要通过大量手写代码才能落地。现在，同样的判断可以快速扩展到多个 Agent、多个页面和多个项目。错误判断也同样会被快速放大。

因此，工程师的责任没有减轻，而是从“亲自完成每一步”转向：

- 定义正确的问题；
- 设计可执行的边界；
- 选择什么交给脚本、什么交给模型、什么必须由人判断；
- 建立反馈循环，让系统从真实错误中改善；
- 在自动化不再可靠时让它停下来。

我不再把“不写代码”理解成“不做工程”。如果我设计了状态、权限、验证、熔断和知识回流，即使大部分实现由 AI 生成，我仍然在完成最核心的工程工作。

## 结语

回头看，我的工作流经历了四次变化：

```text
手写代码 + AI 辅助
        ↓
截图驱动的代码生成
        ↓
Cursor + Figma MCP + 工程 skill
        ↓
Build / Verify Agent + orchestration
```

表面上，这是一段不断减少手写代码的过程。实际上，它是一段不断发现新瓶颈、再把瓶颈变成系统的过程。

最初，我在优化“怎样更快地写出页面”；后来，我开始解决“怎样稳定地交付页面”；现在，我更关心的是“怎样让经验沉淀成下一次可以自动执行的规则”。

也许这就是我目前对 AI 工程最真实的理解：模型负责产生可能性，工程系统负责把可能性约束成可靠结果，而人负责决定什么结果值得被接受。
